# Handoff Generator / Execution Contract

**Status:** CANONICAL SPECIFICATION  
**Project:** AI Bridge  
**Applies to:** every Codex implementation, repair, migration, recovery, and self-development execution  
**Authority:** `docs/constitution/BRIDGE_CONSTITUTION.md`  
**Execution workflow:** `docs/workflows/EVIDENCE_DRIVEN_SPRINT.md`

## 1. Purpose

The Handoff Generator produces the complete, deterministic execution contract required to start a Codex run safely and consistently.

The generated handoff is the bridge between Project Context and Codex execution. It resolves the selected Project, repository state, approved sprint, required governance documents, release gates, evidence paths, and allowed closure states into one immutable execution package.

The handoff does not describe how to implement the sprint. The sprint defines the work; the workflow defines how to execute it; the handoff binds the exact inputs for one execution.

## 2. Core rule

Codex must never infer the active sprint or execution baseline from branch names, filenames, issues, pull requests, roadmaps, comments, chat history, or model memory.

Every governed Codex run must begin from one validated Execution Contract generated by the canonical Handoff Generator.

No valid contract means no implementation start.

## 3. Responsibilities

The Handoff Generator must:

1. resolve the active Project;
2. load and validate Project Context;
3. resolve the target repository and integration branch;
4. resolve the exact approved sprint path;
5. resolve the Constitution and workflow versions and paths;
6. resolve the required architecture, AKB, and context documents;
7. resolve the baseline commit or descendant requirement;
8. resolve repository-wide and sprint-specific release gates;
9. resolve evidence output paths;
10. generate a deterministic handoff identifier;
11. validate that all mandatory inputs exist and are mutually consistent;
12. emit both machine-readable and human-readable representations;
13. refuse generation when a material ambiguity or conflict remains.

## 4. Non-responsibilities

The Handoff Generator must not:

- implement the sprint;
- modify application code;
- choose a sprint based on guesswork;
- approve a sprint;
- silently repair conflicting governance documents;
- merge pull requests;
- write directly to `main`;
- execute release gates;
- create Product Owner decisions;
- replace Project Context;
- replace the Evidence-Driven Sprint workflow;
- act as a generic prompt builder.

## 5. Required input

The generator requires at least:

```text
PROJECT_IDENTIFIER
EXECUTION_INTENT
REQUESTED_TASK_TYPE
REQUESTED_SPRINT_IDENTIFIER_OR_PATH
REQUESTED_TARGET_BRANCH
REQUESTED_INTEGRATION_TARGET
REQUESTED_BY
```

Inputs may be supplied explicitly by the Product Owner or resolved from a validated active Project Context.

### 5.1 Required explicitness

The approved sprint path must be explicit.

The generator may resolve a sprint identifier to a path only through a canonical registry or exact repository lookup rule. It must not select the newest, highest-numbered, most recently modified, or similarly named sprint by assumption.

### 5.2 Supported task types

At minimum:

```text
FEATURE
BUGFIX
MIGRATION
RECOVERY
DOCUMENTATION
RELEASE
SELF_DEVELOPMENT
```

Task type affects required gates and allowed scope but does not weaken governance.

## 7. Contract invariants

A contract is valid only when all are true:

- Project Context status is `VALID`;
- the active Project is unambiguous;
- repository identity matches Project Context;
- target branch and integration target are explicit;
- the baseline commit exists in the target repository;
- the approved sprint document exists;
- the sprint status permits Codex execution;
- the sprint belongs to the selected Project;
- Constitution, workflow, and sprint documents are readable;
- every mandatory additional context path exists or has an explicitly approved equivalent;
- required Release Gates can be resolved;
- evidence paths are deterministic and do not collide with another active execution;
- allowed terminal states exactly match governance rules;
- no material contradiction exists between Project Context, AKB, sprint, and repository state;
- the normalized contract hash can be reproduced.

## 8. Contract lifecycle

Allowed lifecycle states:

```text
DRAFT
VALIDATED
ISSUED
CONSUMED
COMPLETED
SUPERSEDED
REVOKED
```

Rules:

- `DRAFT` is incomplete and cannot start execution;
- `VALIDATED` has passed all pre-issuance checks;
- `ISSUED` is immutable and may start exactly one governed execution unless retry semantics explicitly reuse the same execution identity;
- `CONSUMED` means Codex acknowledged the contract and started preflight;
- `COMPLETED` links to final evidence and closure state;
- `SUPERSEDED` points to a newer contract generated because binding inputs changed;
- `REVOKED` cannot be used.

After issuance, binding fields must be immutable. Changes require a new handoff identifier and contract hash.

## 9. Contract invalidation

An issued contract becomes stale or invalid when any binding input changes materially before execution begins, including:

- approved sprint content changes;
- Constitution or workflow changes;
- target repository HEAD violates the baseline rule;
- active Project changes;
- Project Context becomes `STALE`, `CONFLICTED`, `INCOMPLETE`, or `UNAVAILABLE`;
- target branch or integration target changes;
- required release gates change;
- evidence paths collide;
- the contract is revoked or superseded.

Codex must stop before mutation when contract integrity validation fails.

If implementation has already started and a binding document changes, the run must be classified according to the workflow, the contract must be superseded, and affected work must be reassessed against the new contract.

## 12. Storage and audit

Issued contracts must be stored as immutable execution records in the operational database.

Repository publication is optional and explicit. When evidence policy requires repository-versioned handoffs, publish a sanitized copy under:

```text
docs/evidence/<handoff-identifier>/EXECUTION_CONTRACT.yaml
```

The operational record must retain:

- source Project Context snapshot;
- normalized contract payload;
- contract hash;
- lifecycle transitions;
- issuing actor;
- consuming execution identity;
- final evidence links;
- final closure state.

Secrets and credentials must never be embedded in the contract.

## 13. Required application operations

Implement or reserve these canonical operations:

- `generate_execution_contract`
- `validate_execution_contract`
- `issue_execution_contract`
- `get_execution_contract`
- `render_execution_handoff`

Public operations must be idempotent where appropriate.

Repeated generation with identical normalized inputs may return the same draft representation, but issuance must preserve a unique immutable execution identity.

## 15. Security and safety requirements

- never include tokens, passwords, private keys, or secret environment values;
- preserve unrelated working-tree changes;
- require explicit authorization for destructive or production-risk operations;
- bind execution to exact repository identity and baseline;
- prevent contract reuse across Projects or repositories;
- make contract hash verification mandatory before Codex mutation;
- log lifecycle events without logging secrets;
- do not allow callers to weaken terminal-state or Release Gate requirements through arbitrary input.

## 16. Relationship to Project Context

Project Context answers:

> What Project is active, what is its current state, and where should work continue?

The Handoff Generator answers:

> What exact immutable execution package may Codex use for this one governed run?

A handoff must reference an immutable Project Context snapshot. It must not depend only on mutable current context.

## 19. Minimum acceptance scenarios for implementation

A future implementation sprint must prove at least:

### A. Valid contract generation

Given a selected Project with `VALID` context and an approved sprint, generate a complete contract with deterministic paths and a reproducible hash.

### B. No active Project

Generation fails with `NO_ACTIVE_PROJECT`.

### C. Invalid Project Context

Generation fails for `STALE`, `INCOMPLETE`, `CONFLICTED`, and `UNAVAILABLE` context.

### D. Missing or unapproved sprint

Generation fails without inferring another sprint.

### E. Baseline binding

The contract records the exact repository HEAD and required baseline rule.

### F. Document hash binding

Changing the sprint, Constitution, or workflow produces a different contract hash and invalidates a previously unconsumed contract.

### G. Immutable issuance

An issued contract cannot be edited; changes create a superseding contract.

### H. Project isolation

A contract generated for AI Bridge cannot be consumed for SuperBI or another repository.

### I. Single-consumption protection

A consumed contract cannot start a second independent execution.

### J. Human rendering

The human-readable handoff exactly reflects the machine-readable contract.

### K. Completion binding

Completion records the closure state, final commit SHA, and evidence path.

### L. Secret exclusion

Known secret-like input fields are rejected or omitted from serialized contracts.

## 20. Definition of ready for implementation

The Handoff Generator is ready for implementation when:

- Project Context is implemented and proven;
- this contract is accepted as canonical;
- the repository's sprint approval marker is defined;
- the canonical Release Gate command can be resolved;
- persistence and lifecycle event conventions are available;
- the Product Owner approves a dedicated implementation sprint.
